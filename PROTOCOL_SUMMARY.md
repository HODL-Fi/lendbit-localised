# Lendbit Protocol Summary

## Executive Summary

Lendbit is an upgradeable lending protocol implemented as an EIP-2535 diamond. The protocol lets whitelisted users create positions, deposit collateral, deposit liquidity into token-specific vaults, borrow supported assets, take fixed-tenure loans, repay debt, and liquidate unsafe positions. The system also includes Chainlink-based price valuation, Chainlink Functions request/fulfillment plumbing, and an Aave-style yield allocation layer for collateral.

The protocol has two major accounting domains:

- The diamond-level accounting in `LibAppStorage`, which tracks positions, collateral, supported tokens, vault configuration, borrow balances, loans, oracle configuration, whitelist state, and yield configuration.
- The per-token `TokenVault` accounting, which tracks ERC4626 shares, underlying token balance, vault borrows, accrued interest, bad debt, and pause state.

Most economic correctness depends on those two accounting domains staying synchronized.

## Architecture

### Diamond Proxy

The main entry point is `contracts/Diamond.sol`. It stores the EIP-2535 selector table and dispatches calls to facets through `delegatecall`.

The diamond system is composed of:

- `Diamond.sol`: proxy and selector dispatch.
- `DiamondCutFacet.sol`: owner-gated facet add/replace/remove operations.
- `DiamondLoupeFacet.sol`: facet and selector introspection.
- `OwnershipFacet.sol`: ERC173-style ownership.
- `LibDiamond.sol`: diamond storage, ownership, selector table management, and upgrade logic.
- `DiamondInit.sol`: initializer for interface support.

Application state is not stored in facets directly. Facets share one storage layout through `LibAppStorage.appStorage()`, so all facet calls mutate the diamond's protocol storage.

### Core Facets

The main application facets are:

- `ProtocolFacet`: collateral deposits/withdrawals, borrowing, repayment, tenured loans, signed borrow requests, collateral token configuration, interest-rate configuration, and LTV configuration.
- `VaultManagerFacet`: liquidity deposits/withdrawals, vault deployment, vault upgrade, token support pause/resume, and vault parameter management.
- `PositionManagerFacet`: position creation, position ownership transfer, forced admin transfer, whitelist/blacklist, and request-borrow signer configuration.
- `LiquidationFacet`: liquidatability checks and liquidation of both open-ended borrows and fixed-tenure loans.
- `PriceOracleFacet`: Chainlink feed reads, feed staleness configuration, Chainlink Functions setup, request sending, fulfillment handling, and subscription funding.
- `YieldStrategyFacet`: Aave-style yield configuration, collateral yield rebalancing, user yield claims, and protocol yield harvests.
- `GettersFacet`: read-only protocol views.

Most implementation logic lives in libraries such as `LibProtocol`, `LibVaultManager`, `LibLiquidation`, `LibPriceOracle`, `LibYieldStrategy`, and `LibPositionManager`.

## Main Actors

### Users

Users interact with positions and vaults. A normal user can:

- Deposit liquidity into a supported vault token.
- Withdraw vault liquidity by burning vault shares.
- Deposit supported collateral.
- Withdraw collateral if health factor remains safe.
- Borrow supported tokens.
- Take fixed-tenure loans.
- Repay open-ended borrows and fixed-tenure loans.
- Transfer position ownership.
- Claim yield generated by collateral allocated to the yield strategy.

Many user flows require the caller to be whitelisted.

### Borrowers

Borrowers are users with collateral-backed positions. Borrow capacity is determined by oracle-valued collateral, per-token LTV, existing open-ended debt, and active tenured-loan debt.

The protocol supports two debt types:

- Open-ended borrow balances stored in `s_positionBorrowed[positionId][token]`.
- Fixed-tenure loans stored in `s_loans[loanId]`.

### Depositors

Depositors supply supported borrow assets through `VaultManagerFacet.deposit`. They receive ERC4626 shares from the corresponding `TokenVault`. Their claim depends on the vault's `totalAssets()`, which includes the vault token balance, outstanding borrows, accrued interest, and pending interest.

### Liquidators

Liquidators repay unsafe debt and receive collateral plus a configured liquidation bonus. Liquidation is based on oracle-valued debt and collateral.

### Security Council / Diamond Owner

The diamond owner is the root administrative authority and is treated as the protocol's security council. It can:

- Upgrade facets through diamond cuts.
- Transfer ownership.
- Configure collateral tokens and LTVs.
- Deploy and upgrade token vaults.
- Configure vault interest parameters, utilization, reserve factor, and liquidation bonus.
- Pause/resume supported borrow tokens.
- Whitelist/blacklist users.
- Force-transfer positions.
- Set the signed-borrow signer.
- Configure Chainlink oracle and Functions settings.
- Configure and pause yield strategies.
- Harvest protocol yield.

## Shared Storage Model

All facets use `LibAppStorage.StorageLayout`. Important storage areas include:

- Position ownership:
  - `s_nextPositionId`
  - `s_positionOwner[positionId]`
  - `s_ownerPosition[user]`

- Whitelist and signer state:
  - `isWhitelisted[user]`
  - `s_requestBorrowSigner`
  - `s_requestBorrowNonceUsed[contract][nonce]`

- Supported borrow tokens:
  - `s_allSupportedTokens`
  - `s_supportedToken[token]`
  - `i_tokenVault[token]`
  - `s_tokenVaultConfig[token]`
  - `s_tokenPriceFeed[token]`

- Collateral:
  - `s_allCollateralTokens`
  - `s_supportedCollateralTokens[token]`
  - `s_collateralTokenLTV[token]`
  - `s_positionCollateral[positionId][token]`

- Open-ended debt:
  - `s_positionBorrowed[positionId][token]`
  - `s_positionBorrowedLastUpdate[positionId][token]`

- Tenured loans:
  - `s_nextLoanId`
  - `s_loans[loanId]`
  - `s_positionActiveLoanIds[positionId]`
  - `s_positionClosedLoanIds[positionId]`
  - `s_loanPrincipal[loanId]`
  - `s_loanStartTime[loanId]`

- Oracle and Chainlink Functions:
  - `s_tokenPriceFeed[token]`
  - `s_priceFeedStalenessThreshold[token]`
  - `i_router`
  - `i_linkToken`
  - `s_subscriptionId`
  - `s_donID`
  - `s_source`
  - `s_functionResponse[requestId]`

- Yield:
  - `s_yieldConfigs[token]`
  - `s_positionYield[positionId][token]`

- Reentrancy:
  - `s_reentrancyStatus`

## TokenVault Model

Each supported borrow token has a dedicated `TokenVault`.

`TokenVault` is an ERC4626-style vault whose privileged operations can only be called by the diamond. It tracks:

- `interestRate`
- `totalBorrows`
- `totalAccruedInterest`
- `totalBadDebt`
- `lastUpdateTimestamp`
- `paused`
- ERC20/ERC4626 share balances and total supply

`TokenVault.totalAssets()` returns:

```text
underlying balance + totalBorrows + totalAccruedInterest + pending interest
```

This means vault share price depends on both actual token custody and internal debt accounting. If repayments, liquidations, bad debt, or borrow accounting update only one side, share accounting can become incorrect.

## Main Flows

### Liquidity Deposit

Users deposit supported borrow assets through `VaultManagerFacet.deposit`.

Flow:

1. Validate token support.
2. Create a position for the depositor if needed.
3. Increase `s_tokenVaultConfig[token].totalDeposits`.
4. Transfer tokens from the user to the diamond.
5. Approve the token vault.
6. Call `TokenVault.deposit`.
7. Mint ERC4626 shares to the depositor.

### Liquidity Withdrawal

Users withdraw supported borrow assets through `VaultManagerFacet.withdraw`.

Flow:

1. Validate token support and existing position.
2. Reduce `s_tokenVaultConfig[token].totalDeposits`.
3. Call `TokenVault.withdraw`.
4. Burn user shares.
5. Transfer underlying from the vault to the user.

### Collateral Deposit

Users deposit collateral through `ProtocolFacet.depositCollateral`.

Flow:

1. Validate amount.
2. Require the caller to be whitelisted.
3. Create a position if the caller has none.
4. Require token support as collateral.
5. Increase `s_positionCollateral[positionId][token]`.
6. Transfer ERC20 collateral to the diamond, unless using the native-token sentinel.
7. Rebalance collateral into the yield strategy if configured.

### Collateral Withdrawal

Users withdraw collateral through `ProtocolFacet.withdrawCollateral`.

Flow:

1. Resolve caller position.
2. Ensure sufficient recorded collateral.
3. Decrease recorded collateral.
4. Recompute health factor.
5. Revert if debt exists and health factor would fall below the minimum.
6. Withdraw/rebalance yield allocation if needed.
7. Transfer collateral to the user.

### Open-Ended Borrow

Users borrow through `ProtocolFacet.borrow`.

Flow:

1. Resolve caller position.
2. Require supported borrow token.
3. Check vault utilization against `s_tokenVaultConfig[token]`.
4. Price the requested borrow amount in USD.
5. Check health factor after including new debt.
6. Update `s_positionBorrowed`.
7. Update `s_positionBorrowedLastUpdate`.
8. Update diamond-level vault borrows.
9. Call `TokenVault.borrow`, which transfers tokens from the vault to the borrower.

### Open-Ended Repay

Users repay through `ProtocolFacet.repay`.

Flow:

1. Resolve caller position.
2. Calculate current debt with accrued interest.
3. Cap repayment to outstanding debt.
4. Reduce `s_positionBorrowed`.
5. Update `s_positionBorrowedLastUpdate`.
6. Reduce diamond-level vault borrows.
7. Call `TokenVault.repay`.
8. Transfer repayment tokens from the user to the vault.

### Fixed-Tenure Loan

Users can create fixed-tenure loans through `takeLoan` or `requestBorrow`.

`takeLoan` is caller-driven. `requestBorrow` is signature-driven and validates:

- action string
- position id
- token
- amount
- tenure
- source chain id
- target chain id
- nonce
- contract address
- wallet
- configured signer

Loan creation flow:

1. Validate position, token support, tenure, utilization, collateral value, and health factor.
2. Create a `Loan` record with status `FULFILLED`.
3. Increment `s_nextLoanId`.
4. Append the loan id to `s_positionActiveLoanIds[positionId]`.
5. Increase diamond-level vault borrows.
6. Call `TokenVault.borrow`.

### Fixed-Tenure Loan Repayment

Users repay loans through `repayLoan` or `repayLoanFor`.

Flow:

1. Validate caller/position relationship.
2. Load the loan.
3. Compute outstanding balance as principal plus tenure interest plus post-maturity penalty.
4. Cap repayment to outstanding debt.
5. Update loan repaid amount, principal, and start timestamp.
6. If fully repaid, mark loan `REPAID`, remove it from active loans, and append it to closed loans.
7. Transfer tokens from the payer to the vault.
8. Reduce diamond-level vault borrows.
9. Call `TokenVault.repay`.

### Liquidation

The protocol supports liquidation of:

- Open-ended position debt.
- Fixed-tenure loans.

Liquidatability is checked by comparing debt value against collateral value times the liquidation threshold.

Liquidation flow:

1. Confirm the position or loan is liquidatable.
2. Confirm selected collateral exists.
3. Validate liquidator allowance and balance.
4. Convert repayment amount into collateral amount using oracle prices.
5. Add the configured liquidation bonus.
6. Reduce recorded collateral.
7. Rebalance yield allocation for withdrawn collateral.
8. Reduce loan or open-ended debt state.
9. Transfer repayment tokens into the relevant vault.
10. Transfer seized collateral to the liquidator.

## Oracle System

The protocol uses Chainlink AggregatorV3 feeds for token valuation.

Price reads validate:

- Feed address is configured.
- Answer is positive.
- `answeredInRound` matches the round.
- `updatedAt` is within a token-specific or default staleness threshold.

Valuation is used for:

- Collateral value.
- Borrowed value.
- Borrow capacity.
- Health factor.
- Liquidation eligibility.
- Liquidation collateral conversion.

The oracle facet also stores Chainlink Functions configuration and request/response state. Fulfillment is restricted to the configured router.

## Yield Strategy

The yield strategy integrates collateral with Aave-style pools.

For each configured token, the protocol stores:

- Whether yield is enabled.
- Whether yield is paused.
- Pool address.
- aToken address.
- Allocation basis points.
- Protocol share basis points.
- Total principal allocated.
- Accumulated yield index.
- Protocol-accrued yield.
- Last aToken balance.

Position-level yield state tracks:

- Principal allocated for that position.
- User-accrued yield.
- Entry accumulator.

Collateral deposits, withdrawals, and liquidations can trigger yield rebalancing. Users can claim their yield share; the security council can harvest the protocol share.

## Access Control

The main authority is `LibDiamond.contractOwner()`.

The owner/security council controls:

- Diamond upgrades.
- Vault deployment and upgrade.
- Vault risk parameters.
- Token support pause/resume.
- Collateral token registration and LTV.
- Interest and penalty rates.
- User whitelist/blacklist.
- Position force-transfer.
- Signed-borrow signer.
- Oracle and Chainlink Functions configuration.
- Yield configuration and protocol yield harvesting.

User-facing protocol operations usually require whitelist membership through library checks, especially position-related lending and borrowing actions.

## Important Invariants

The protocol should maintain these high-level invariants:

- A user should have at most one active position.
- `s_ownerPosition[user]` and `s_positionOwner[positionId]` should remain reciprocal.
- Supported token state should map consistently to a vault, price feed, vault config, and support flag.
- Supported collateral state should map consistently to a price feed, LTV, and collateral support flag.
- Diamond-level vault accounting should stay consistent with `TokenVault` accounting.
- Vault shares should represent a pro-rata claim on real `TokenVault.totalAssets()`.
- Borrow capacity and utilization should use consistent total deposit and total borrow bases.
- Open-ended borrows and fixed-tenure loans should both count toward health factor and liquidation.
- Repayment and liquidation should reduce the same debt that was actually repaid.
- Oracle values should normalize both token decimals and feed decimals correctly.
- Yield principal and accrued yield should remain conserved across position-level and token-level strategy state.
- Diamond upgrades should not corrupt app storage, selector routing, token vault mappings, or user accounting.

## Main Risk Surfaces

The most important engineering risk is accounting divergence between the diamond and token vaults. Borrow, repay, liquidation, bad-debt, vault upgrade, and yield flows all cross the boundary between protocol-level state and vault-level state.

Other important risk surfaces include:

- Diamond upgrades and storage layout compatibility.
- Oracle decimal and staleness assumptions.
- Health-factor and liquidation math.
- ERC4626 share price correctness.
- Non-standard ERC20 behavior.
- Native-token sentinel handling.
- Position ownership transfer integrity.
- Chainlink Functions request/fulfillment authorization.
- Aave-style yield integration and external pool failure modes.
- Security council key management and ownership transfer safety.

## Tests

The test suite covers the major protocol flows:

- Diamond deployment.
- Vault deposits and withdrawals.
- `TokenVault.totalAssets()` behavior.
- Borrow and repay flows.
- Fixed-tenure loan creation and repayment.
- Liquidation success and revert cases.
- Oracle price reads and token decimal normalization.
- Position collateral accounting.
- Yield strategy allocation, withdrawal, claim, harvest, and deficit behavior.

Notable gaps include:

- No broad invariant/fuzz harness across arbitrary deposit, borrow, repay, liquidation, bad-debt, yield, and upgrade interleavings.
- Limited coverage of non-standard ERC20 tokens.
- Limited end-to-end Chainlink Functions behavior.
- Limited adversarial oracle timing coverage.
- Limited storage-layout and malicious/incorrect facet upgrade testing.
- Yield tests use mock Aave-style pools rather than real integration behavior.

## Mental Model

Lendbit can be understood as three connected ledgers:

1. Position ledger: who owns each position, what collateral it holds, and what debt it owes.
2. Vault ledger: how much liquidity depositors supplied, how many shares they own, how much has been borrowed, and how much interest has accrued.
3. External-value ledger: oracle prices and yield strategy balances that decide whether positions are safe and how collateral/yield should be valued.

The protocol is healthy only when all three ledgers agree after every user action, liquidation, admin action, and external integration call.
